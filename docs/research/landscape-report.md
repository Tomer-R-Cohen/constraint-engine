# Nobody ships the general chat-to-solver engine yet

No mature product found in this research does the full loop: upload spreadsheets, state rules in plain language, have an LLM compile them into a checked constraint model, solve, and explain the result to a non-expert for any "assign X to Y" problem. The market has split into three partial layers. Solver vendors build LLM copilots for modelers (Gurobi's Modeler, IBM's Modeling Assistant). Workforce apps add chat agents that run fixed rule settings (Deputy AI, ShiftScheduler.ai). A spread of MCP servers lets general chatbots call solvers. None of them combines spreadsheet ingestion, a rule layer that is safe for non-programmers, plain-language conflict explanation, and alternative options across rostering, timetabling and placement. The research supports the architecture Shibutzit already uses. When an LLM writes free-form solver code, about **50–75%** of models are correct on clean benchmarks and **under 50%** on realistic rule-heavy problems, and the errors are mostly silent. Template- and catalog-based extraction reaches about **90%** on workforce scheduling. So the fork should generalize the existing catalog rather than replace it with code generation. The recommended path keeps Python and CP-SAT, adopts an XHSTT-style JSON spec with a closed catalog of about eleven constraint shapes, and ports the app's current seven rules into that catalog as the "placement" template. It then adds rostering and timetabling shapes in that order, each tested against public benchmarks.

## Three partial layers, and no end-to-end product

The closest commercial products each cover one part of the loop. Gurobi's February 2025 "AI Modeling" custom GPTs turn plain-text problem descriptions into gurobipy code, so the LLM writes free-form code for an analyst to run ([Gurobi newsroom](https://www.gurobi.com/company/newsroom/gurobi-ai-modeling-empowers-users-with-accessible-optimization-resources)). Its later Intelligence Hub adds a "Modeler" agent (beta), an "Explainer" for infeasibility diagnosis (experimental), and an experimental local MCP server ([EfficientlyConnected](https://www.efficientlyconnected.com/gurobi-intelligence-hub-ai-agents-optimization/)). The Modeler is the most mature design seen. It builds a structured spec (Overview, Objective, Constraints, Input data, Output format, Test scenarios, Out-of-scope) by asking one clarifying question at a time, generates code plus **one pytest per scenario**, and stops to ask the user when spec, code and tests disagree ([Gurobi Modeler docs](https://docs.gurobi.com/projects/intelligence/en/current/modeler.html)). It is built for analysts with a Gurobi licence, not for a school principal. IBM's Decision Optimization Modeling Assistant takes the other route. The user **first selects a decision domain** and is then guided through templates, in English only ([IBM docs](https://www.ibm.com/docs/en/DSXDOC/DO/DODS_Mdl_Assist/exhousebuildintro.html)). It is the closest enterprise version of a fixed rule catalog.

Timefold, the former OptaPlanner team, raised a **$13M Series A in July 2026**. Its copilot "lets planners interrogate schedules in natural language" over prebuilt, domain-specific models ([KOMPAS VC](https://www.kompas.vc/news/why-we-invested-in-timefold)). Its public position is that "LLMs can't optimize schedules, but AI can": the LLM should call a deterministic solver through tool calling or MCP ([Timefold blog](https://timefold.ai/blog/llms-cant-optimize-schedules-but-ai-can)). No evidence was found that its copilot creates new constraint types from chat. Among workforce apps, Deputy AI builds, edits and publishes schedules through conversation ([Deputy](https://deputy.com/ai)). It almost certainly drives Deputy's existing auto-scheduler and fixed award rules, though the help article could not be fetched to confirm this. ShiftScheduler.ai is the closest small match: rostering on **Google OR-Tools**, custom rules set through setup steps, chat requests such as "schedule this date range", and a built-in MCP server, for **€1–2 per seat per month** ([shiftscheduler.ai](https://shiftscheduler.ai/)). Its scope is still shift rostering with a fixed rule set. School timetabling vendors such as TimetableMaster advertise chat agents and claim 50,000+ institutes, but publish **no technical detail** on the solver or on how chat maps to constraints ([TimetableMaster](https://www.timetablemaster.com/timetable-generator-ai)).

Open source splits along one line: does the LLM write code, or does it fill a schema? OptiMUS from Stanford ([GitHub](https://github.com/teshnizi/OptiMUS)), Microsoft's OptiGuide/OptiMind ([GitHub](https://github.com/microsoft/OptiGuide)) and mcp-solver v4 all have the LLM write solver code. mcp-solver moved from validated item-by-item MiniZinc edits (v1–v3) to a Python "solver-writing agent" in v4 ([GitHub](https://github.com/szeider/mcp-solver)). That shows its research authors now trust stronger LLMs with free code, but on benchmark puzzles, not on rules a user owns. The schema pattern appears only in toys. One example is slimaneoptic/shift-scheduler, where an LLM emits changes that must pass "a strict JSON schema" before CP-SAT runs. It has zero stars and three commits ([GitHub](https://github.com/slimaneoptic/shift-scheduler)). The consumer default is still pasting an Excel template into ChatGPT, which gives no feasibility guarantee ([RosterElf](https://www.rosterelf.com/blog/create-staff-rota-excel-using-chatgpt)).

The research found **no LLM-plus-solver product for student class placement** and no one offering "manager-owned rules → checked model → solve → explain trade-offs" across domains. Two caveats: the search did not cover Product Hunt, Hacker News or Israeli school tools, and incumbents are clearly moving toward this space. The opening is real, but it may not last.

## Free-form model generation fails silently on real rules

Academic accuracy numbers explain why the vendors stop short. On CP-Bench (now DCP-Bench-Open, published in JAIR), zero-shot accuracy is about **57% for MiniZinc** and **65–75% for Python targets** (CPMpy, OR-Tools). With gpt-5.1 on CPMpy, repeated sampling plus self-verification lifts this from **70.1% to 90.2%** ([arXiv 2506.06052v3](https://arxiv.org/html/2506.06052v3)). (An earlier version of the paper reported lower OR-Tools figures, about 50%, so the ranking of OR-Tools against CPMpy depends on the version ([v2](https://arxiv.org/html/2506.06052v2)).) The same study found a more worrying effect. Checked on one default instance, gpt-5.1 scored 78.3%. Checked on several instances of the same problem, it scored **60.9%**, because LLMs "frequently overfit to specific values" instead of writing a general model. Richer API documentation reduced runtime errors but *increased* logical modeling errors, and retrieving similar examples often lowered accuracy ([arXiv 2506.06052v3](https://arxiv.org/html/2506.06052v3)). Text2Zinc shows the same gap between code that runs and code that is right: chain-of-thought prompting reached **58.7% execution accuracy but only 25.4% solution accuracy** ([arXiv 2503.10642](https://arxiv.org/pdf/2503.10642)). Most models that ran still gave wrong answers.

Realistic rule sets do worse. A 2025 survey found that **IndustryOR labels were 54% wrong** and NL4Opt's 26% wrong. On the cleaned sets, methods scored about **31–43% on IndustryOR** ([survey, arXiv 2508.10047](https://arxiv.org/pdf/2508.10047)). R2C, the state of the art on a benchmark built from rich operational rules, reaches **47.2%** ([arXiv 2602.02029](https://arxiv.org/abs/2602.02029)). So a product that lets an LLM freely model a school's or hospital's real policy should expect roughly one model in two or three to be wrong somewhere. Most of those wrong models still produce a plausible-looking schedule.

Letting the LLM produce the schedule directly is worse still. SCHEDBench validated LLM-written schedules with CP-SAT. The best model reached 55.9% feasibility, the median across 13 models was **15.2%**, and curriculum timetabling (ITC) averaged **0.4%** ([arXiv 2608.00991](https://arxiv.org/html/2608.00991v1)). The same benchmark found that **reordering equivalent constraint text changed violation rates** beyond seed noise, so phrasing alone moves results. This matters for any engine that passes user wording straight to the model.

Constraining what the LLM produces is what works. SMILO tested workforce scheduling in manufacturing, logistics and services. It identifies the relevant modeling components, uses the LLM only to extract problem-specific parameters, and builds the model from expert templates. It produced **correct models in 90% of instances, more than 35 points above direct generation** ([arXiv 2511.02364](https://arxiv.org/abs/2511.02364)). OptiChat combines predefined functions with limited code generation and scored 84.3% overall. When its predefined functions were removed in an ablation, **diagnosis and sensitivity accuracy fell to 0%**. The one capability left to code generation ("why-not" queries) scored only 62.2% ([arXiv 2501.08406](https://arxiv.org/html/2501.08406v2)). OptiChat's failures were also informative: **31% were wrong tool choices**, so a small catalog with clearly distinct entries matters as much as broad coverage. In 2026 the research focus moved to checking models after generation. Examples are semantic checker agents (CP-SynC, +11 to +21 points) ([arXiv 2605.01675](https://arxiv.org/pdf/2605.01675)), a hallucination taxonomy with specialist auditor agents (OptArgus) ([arXiv 2605.11738](https://arxiv.org/pdf/2605.11738)), and repair guided by a minimal unsat core, which cut fabrication in weaker models from **79% to 7%** ([arXiv 2608.14771](https://arxiv.org/abs/2608.14771)). One caveat: no study compares a fixed catalog head-to-head with checked free CPMpy code on the same scheduling rules, and nothing was found on Hebrew or other non-English rule statements.

## Eleven constraint shapes cover rostering, timetabling and placement

The mature formats share the same structure. XHSTT, the ITC2011 high-school format, models any problem as **Times** (with time groups such as "Monday" or "afternoons"), **Resources** of user-defined types (Teacher, Room, Class, Student) with resource groups, **Events** whose time and resource slots are either preassigned or open, and a set of **typed, parameterized Constraints**. It has 15 constraint types, from Assign Resource to Limit Workload ([Post et al. 2013](https://www2.cs.sfu.ca/~mitchell/cmpt-827/2015-Fall/Projects/TT-ITC-2011-Report.pdf)). Crucially, **no constraint type is inherently hard or soft**. Each instance carries its own hard flag and weight, and solutions are compared on infeasibility first, then on the objective ([arXiv 2407.16898](https://arxiv.org/pdf/2407.16898)). INRC-II nurse rostering uses the same core with days as time groups, skills as resource attributes, and coverage as demand per (day, shift, skill). It adds one important idea: **contracts**, named rule bundles that nurses reference instead of carrying their own rules ([arXiv 1501.04177](https://ar5iv.labs.arxiv.org/html/1501.04177)). ITC2019 adds student sectioning, which assigns students to classes and is structurally Shibutzit's problem ([DTU MIP paper](https://backend.orbit.dtu.dk/ws/files/221992887/A_MIP_Formulation_of_the_International_Timetabling_Competition_2019_Problem.pdf)). FET expresses hardness as a weight percentage, where 100% means the rule must hold ([FET FAQ](https://lalescu.ro/liviu/fet/doc/en/faq.html)). Timefold's employee model adds a **medium score tier** for "assign as many mandatory shifts as possible". The solver then reports unfilled demand instead of failing ([Timefold docs](https://docs.timefold.ai/employee-shift-scheduling/latest/user-guide/constraints)).

XHSTT also carries a warning. ITC2011 drew 5 submitting teams against about 40 active teams for ITC2007, and the organizers blamed "the complexity of the format" ([Post et al. 2013](https://www2.cs.sfu.ca/~mitchell/cmpt-827/2015-Fall/Projects/TT-ITC-2011-Report.pdf)). The fork should adopt XHSTT's *concepts* in its own small JSON schema, not its XML. The most portable CP-SAT idea comes from OR-Tools' own shift-scheduling example. Its 7-tuple **band** `(hard_min, soft_min, min_cost, soft_max, hard_max, max_cost)` bounds counts, weekly sums and run lengths ([OR-Tools example](https://raw.githubusercontent.com/google/or-tools/stable/examples/python/shift_scheduling_sat.py)). One parameterized constraint then covers both "hard" and "soft", so the catalog does not need separate types for each.

Combining the domain vocabularies (INRC-II, XHSTT, ITC2019, FET, Timefold, OR-Tools) gives the catalog below. Every entry is a selector (which entities, resources or slots) plus parameters, a per-instance mode, and a priority level. The right-hand column shows where Shibutzit's current rules fit. The grouping is this report's synthesis of the cited formats, not a published standard.

| # | Shape | Typical rules | Shibutzit today |
|---|---|---|---|
| 1 | Coverage / cardinality band | min/max/target staff per shift; class size | `capacity`, `at_least_one_of` |
| 2 | No-overlap | one shift per day; teacher/room/class clash | (implicit: one class per student) |
| 3 | Eligibility / availability / fixed | skills, unavailable times, preassignment | `locked` |
| 4 | Count band over a window | max shifts per week, lessons per day, weekends worked | — |
| 5 | Sequence / run length | max consecutive days, min days off | — |
| 6 | Transitions / rest | no night→morning; min rest | — |
| 7 | Gaps / compactness | teacher idle periods, complete weekends | — |
| 8 | Spread / distribution | a course's lessons on distinct days | — |
| 9 | Relational (same/different/together/apart/precedence) | same room, students together or apart | `separate`, `together` |
| 10 | Balance / fairness | equal shifts per employee; gender/level per class | `balance` |
| 11 | Preference / request | shift wishes, room preferences, friendships | friendship objective |

Two variable directions appear in these formats: resource → slot (rostering Booleans x[e,d,s]) and event → slot/resource (timetabling). Both reduce to Boolean assignment literals in CP-SAT, so one compiler can host both. The current app is the "entity → bin" special case. Its seven rules fall into shapes 1, 3, 9, 10 and 11, so it becomes the first template rather than a rewrite.

## Code, not the LLM, owns meaning, explanations and numbers

The architecture research shows a consistent pattern: let the LLM choose and fill structured operations, and let trusted code own everything that has to be true. For **verification**, U-Define found that typed hard and soft constraints improved perceived usefulness and satisfaction, but **numeric weights confused users**. It recommends back-translating formalized rules into plain language for confirmation ([arXiv 2605.02765](https://arxiv.org/abs/2605.02765)). VeriPlan does the same with formal templates ([arXiv 2502.17898](https://arxiv.org/pdf/2502.17898)). Timefold's score analysis attaches per-constraint matches and the specific entities to each result, to explain "why a particular assignment wasn't made" ([Timefold docs](https://docs.timefold.ai/timefold-solver/latest/constraints-and-score/understanding-the-score)). In practice, each catalog type should carry a paraphrase template written in code, in Hebrew and English. Priorities should be ordinal levels, not raw weights. A solver-independent Python checker should re-evaluate every rule on every returned assignment.

For **infeasibility**, the toolkit is mature. CP-SAT's `sufficient_assumptions_for_infeasibility()` returns a conflicting set of assumptions, but the result is not guaranteed minimal ([CP-SAT Primer](https://d-krupke.github.io/cpsat-primer/parameters.html)). That is why CPMpy layers deletion-based `mus`, preference-ordered `quickxplain`, and weighted `mcs`/`mss` on top of solver cores ([CPMpy explain](https://cpmpy.readthedocs.io/en/latest/api/tools/explain.html)). The IJCAI survey finds that a bare minimal conflict is often unintuitive. Users "want to be shown which subsets of their constraints they can satisfy and which they cannot" ([IJCAI 2021](https://www.ijcai.org/proceedings/2021/601)). This fits the owner's principle that the manager owns the rules. A correction subset can be computed and presented as a *description of the conflict*, for example "these three rules cannot all hold for this data; here is what each option leaves unmet", without telling the manager which rule to drop. OptiChat's "minimal parameter adjustments" is the opposite style ([arXiv 2501.08406](https://arxiv.org/html/2501.08406v2)), and the fork should keep it out of user-facing text. The Timefold-style medium tier is the other half of the answer. When required demand is reported as explicit holes instead of an INFEASIBLE status, there is always a schedule to show and explain.

For **alternatives and refinement**, the standard techniques are Hamming-distance diversity between solutions ([arXiv 1108.3260](https://arxiv.org/pdf/1108.3260)) and minimal-perturbation re-solving. Timefold productizes the latter as pinning plus a per-change disruption penalty ([Timefold docs](https://docs.timefold.ai/timefold-solver/latest/responding-to-change/non-disruptive-replanning)). CP-SAT hints speed up re-solves but can be lost in presolve ([CP-SAT Primer](https://d-krupke.github.io/cpsat-primer/parameters.html)). Shibutzit's rounds of three, with a minimum assignment distance, already implement the first technique. "Refine option B" should add the change penalty.

For **ingestion**, LLM table understanding "drops sharply on long tables and under shuffled rows or columns" ([MMTU, arXiv 2506.05587](https://arxiv.org/html/2506.05587v3)). OptiGuide avoids sending proprietary data to the LLM at all ([arXiv 2307.03875](https://arxiv.org/abs/2307.03875)). The safe pipeline is: parse deterministically; send the LLM only headers, samples and column statistics; let it propose an entity/attribute/relation mapping; check referential integrity in code; and show a confirmation card with counts and mismatches. For **numbers in replies**, OptiGuide's rule applies: the solver computes and the LLM only phrases. Tool arguments should use strict schemas with enums of real entity IDs. For **scale**, CP-SAT has produced feasible healthcare rosters with about **180k variables** ([arXiv 2608.30419 summary](https://www.opentrain.ai/papers/from-metaheuristics-to-exact-methods-a-cp-sat-approach-for-multi-objective-healt--arxiv-2608.30419/); secondary source), and one nurse-rostering study found **90–120 s** the best quality/wait trade-off ([Undip](https://eprints2.undip.ac.id/id/eprint/46608/)). The fork should also follow Nextmv and Gurobi in treating the spec as versioned software with scenario and acceptance tests ([Nextmv](https://nextmv.io/test)).

## What the fork should build on, reuse and build first

**Build on** Python, FastAPI and OR-Tools CP-SAT. Do not adopt Timefold or a free-code agent as the core. Timefold's constraint streams are Java/Python code, not a spec a manager can read back, and free generation brings the silent-error rates above. CPMpy's explain module is worth adding, either as a dependency or as a reference for porting deletion-MUS, QuickXplain and weighted MCS onto the existing assumption literals. Use the CP-SAT shift-scheduling example as the reference for band and sequence helpers. Use public instances as regression corpora: XHSTT datasets from UTwente, INRC-II, and the Curtois nurse instances, which CPMpy can load ([CPMpy datasets](https://cpmpy.readthedocs.io/en/logo/api/tools/datasets/nurserostering.html)).

**Reuse from the current app** the parts that already match the evidence-backed pattern:

- `src/optimizer.py`: one assumption literal per rule, with conflict tracing.
- `backend/llm/tools.py`: strict per-rule tool schemas, with `args_to_constraint` and `_resolve_group` rejecting columns that don't exist. Generalize these into catalog-driven schema generation.
- `src/decision_support.py`: `verify_assignment` (the independent checker), `PortfolioSearch` and `assignment_distance` (diversity), and `rank_tradeoffs`.
- `backend/rounds.py`: rounds of three and refine.
- `src/column_mapping.py`, `src/dataset_schema.py` and `src/validation.py`: the start of the ingestion pipeline. Today they assume one student table and need to become multi-sheet and entity-typed.
- `src/feasibility.py`: pre-solve sanity checks.
- `src/constraints.py`: the Hebrew paraphrase helpers, as the model for code-written back-translation.
- The narration layer and the frontend workspace (conversation, options board, constraint browser).

The prompt rule "explain, never suggest rule changes" carries over unchanged as a product principle.

**Adopt this spec:** a JSON document with:

- `slots`, `slot_groups`, `resource_types`, `resources` and `resource_groups`
- `demands`/`events` with roles
- `rule_bundles`, as INRC-II contracts
- `constraints[]` entries of the form `{type ∈ catalog, applies_to selector, params (band where numeric), mode hard|soft, priority level}`
- a reserved "unfilled demand" tier above the soft tiers

Store it versioned, with data hash, solver version, parameters and seed attached to each result. Use the eleven-shape catalog above, and keep the tool list small with clearly distinct descriptions, because tool misclassification is a third of failures. A domain template is a catalog subset, an entity schema, default priorities and example scenarios. New shapes are added in code, never by the LLM.

**Build order:**

1. **Extract the spec and compiler from today's app** with no behavior change. Port the seven current rules into catalog shapes 1, 3, 9, 10 and 11, and prove identical results on existing test fixtures.
2. **Build the agent eval harness** before adding any new domain: golden (spreadsheet, transcript) → expected spec and solution properties, run on every prompt or model change. This includes Hebrew phrasings and reordered rule text, to measure the SCHEDBench order effect.
3. **Generalize ingestion** to multi-sheet entity mapping with referential checks and a confirmation card. Persist mappings so next term's file reuses them.
4. **Add rostering:** shapes 2 and 4–6, the unfilled-demand tier, and band helpers. Test against the OR-Tools example and INRC-II instances.
5. **Upgrade explanation:** shrink CP-SAT cores to MUS, compute weighted MCS, and render both through paraphrase templates as conflict descriptions, never recommendations. Add per-rule checker output to every option card.
6. **Add timetabling:** time × resource events, plus shapes 7 and 8 and the precedence part of shape 9. Test against XHSTT instances with 60–120 s budgets.
7. **Only then, if rule coverage data shows a real need, add a narrow escape hatch.** This is an expression mini-DSL over catalog selectors (linear counts and sums), parsed and checked against an AST whitelist, marked "unverified" until the manager confirms its paraphrase and a concrete test case. It is not arbitrary Python, which would need microVM sandboxing ([Modal](https://modal.com/resources/best-sandboxed-environments-ai-code-generation)).

## Conclusion

The question has shifted from "can an LLM write a scheduling model?" to "who guarantees the model means what the manager meant?" Incumbents answer with analyst-facing code plus tests (Gurobi) or with fixed domain models plus a querying copilot (Timefold, Deputy). Neither serves a non-expert who owns the rules and needs them honored as written. Shibutzit's constraint that the app must never suggest rule changes looked like a limitation, but it is the product's strongest differentiator. It forces exactly what the evidence favors: a closed vocabulary, code-written meaning and paraphrase, solver-computed numbers, and conflicts explained instead of negotiated away.

The main risk is not technical feasibility. CP-SAT, the shapes and the explanation algorithms are all proven. The unknown is coverage: what share of real managers' rules fit eleven shapes, and how the LLM handles Hebrew rule statements. No published study measures either. The eval harness and rule-coverage logging in steps 2 and 7 should run from the first week, because they are what will tell the fork whether to stay catalog-only or add the escape hatch.
